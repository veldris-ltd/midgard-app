## What Midgard is

Midgard is a core platform, *the enclosure*, and four products that build on it:

- **Midgard**: identity, the object fabric (typed objects, links and actions), governance and post-quantum cryptography (ML-KEM, ML-DSA and SLH-DSA with X25519) applied by default.
- **Forge**: data operations. Syncs files, PostgreSQL and S3-compatible stores into versioned datasets and on into the fabric.
- **Mimir**: local AI. Serves inference inside the enclosure from a signed model.
- **Bifrost**: delivery. Records the fleet and packs signed offline bundles.
- **Heimdall**: operational fusion. Fuses signed observations from feeds into one picture.

It is a 70-crate Rust workspace with console UIs in TypeScript. The gateway edge serves the object fabric: markings are enforced per object, a login returns an ML-DSA-signed session token, and every request is written to one PQ-signed audit ledger. Five services run today (`http-gateway`, `mimir-server`, `bifrost-fleet`, `heimdall-feed` and `forge-worker`); most other subsystems are tested libraries. The [claims ledger](docs/compliance/CLAIMS.md) gives the status of each capability and the evidence for it, and the [overview](docs/guides/OVERVIEW.md) and the [Solutions Architecture Documents](docs/dev/README.md) describe the design.

## Quick start

The fastest path to a running enclosure is docker compose. You need Docker with Compose v2 and `just`. Everything builds offline inside the pinned toolchain image, from the vendored crates.

```bash
git clone https://github.com/veldris-ltd/midgard-app.git midgard && cd midgard
```

```bash
docker build -t midgard-acceptance:1.82.0 deploy/acceptance
```

```bash
just compose-up
```

The two builds fetch their base images the first time; compiling the services needs no network. `just compose-up` builds the services, creates the enclosure's keys and identities, starts all five services and waits until each is healthy. Check it:

```bash
curl -s http://127.0.0.1:7710/api/v1/health
```

```bash
just compose-probe
```

The probe makes one post-quantum mutual TLS (PQ-mTLS) inference call to `mimir-server` and prints the model, the audit sequence number and the completion.

Other ways in:

| You want | Do this | Needs |
|---|---|---|
| A guided install on a Linux server | `sudo deploy/installer/mg-install` ([installer guide](deploy/installer/README.md)) | Ubuntu, Debian or RHEL family; 4 cores, 8 GB |
| To try the console with demo data | `just gateway-http`, then `just console-midgard-http` ([development mode](docs/guides/RUNNING.md#development-mode-the-gateway-edge-and-console)) | Rust 1.82, Node 22.12 or later, pnpm 9.12.0 |
| The services on Kubernetes | `just kind-up`, then `just kind-smoke` ([kind](docs/guides/RUNNING.md#run-on-kubernetes-with-kind)) | Docker, kind, Helm, kubectl |

| For | You need |
|---|---|
| Building and testing | Docker and the pinned image above, or Rust 1.82 and [`just`](https://github.com/casey/just) locally. Every dependency is vendored (`vendor/`), so builds and tests need no network. |
| The consoles | Node 22.12 or later and pnpm 9.12.0 |

## Running it

Under compose the services are:

| Service | What it does | Reach it |
|---|---|---|
| `gateway` | The HTTP edge over the object fabric, its audit ledger and its users | `http://127.0.0.1:7710` from the host |
| `mimir-server` | Inference over PQ-mTLS | internal network only; `just compose-probe` |
| `bifrost-fleet` | The fleet manager agents check in with | internal network only |
| `heimdall-feed` | Fuses signed observations into the operating picture | internal network only |
| `forge-worker` | Runs the jobs in `deploy/compose/forge/jobs.json` and syncs them into the fabric | internal network only |

The gateway speaks plaintext HTTP and binds loopback only unless started with `--allow-non-loopback`. Reach it from another machine only through an SSH tunnel or behind TLS termination.

Day-to-day commands:

```bash
docker compose -f deploy/compose/compose.yaml ps
```

```bash
docker compose -f deploy/compose/compose.yaml logs -f gateway forge-worker
```

```bash
just compose-down
```

`just compose-down` stops the services and keeps their volumes; `just compose-up` starts them again on the same state. `just compose-smoke` runs a full check on throwaway volumes and removes them afterwards.

Try the other services:

```bash
docker compose -f deploy/compose/compose.yaml run --rm fleet-agent --channel stable --version 0.1.0
```

```bash
docker compose -f deploy/compose/compose.yaml run --rm feed-source --kind air-track --entity AC-7 --attrs speed=410,callsign=ALPHA1
```

```bash
docker compose -f deploy/compose/compose.yaml run --rm picture
```

**The console.** The Midgard console runs against a gateway in development mode, which seeds demo data and two logins (`operator` / `midgard-demo` and `approver` / `midgard-approve`) and listens on loopback only:

```bash
pnpm install
```

```bash
just gateway-http
```

```bash
just console-midgard-http
```

Then open http://localhost:5173 (it must be that port). The other six consoles run on built-in sample data only. Serving your own users from a state directory, enrolling administrators, a real model (Granite on llama.cpp), the limits of each mode and troubleshooting are in [docs/guides/RUNNING.md](docs/guides/RUNNING.md).

## Ingesting data

There are three ways in. There is no HTTP import API on the gateway.

**Files, with `mg-admin import`.** The enclosure's schema comes from `ontology.json`, and `mg-admin import` loads a JSON Lines file of objects and links with the gateway stopped. Every record is checked against the ontology before anything is written, and one bad line refuses the whole file. Every keystore command reads its passphrase from the file `MIDGARD_KEYSTORE_PASSPHRASE_FILE` names (at least 16 bytes, readable by its owner only, kept away from the state directory):

```bash
cargo build --release -p http-gateway -p mg-admin
(umask 077; head -c 32 /dev/urandom | base64 > "$HOME/.midgard-passphrase")
export MIDGARD_KEYSTORE_PASSPHRASE_FILE="$HOME/.midgard-passphrase"
./target/release/mg-admin init --state-dir ./enclosure
python3 samples/convert.py ontology > ./enclosure/ontology.json
cp samples/1-configuration/midgard/policy.json ./enclosure/policy.json
python3 samples/convert.py import > samples.jsonl
./target/release/mg-admin import --state-dir ./enclosure --file samples.jsonl
```

This loads the recorded [sample datasets](samples/README.md). For your own data, [Import your own data](docs/guides/IMPORT_YOUR_OWN_DATA.md) covers both file formats (published as JSON Schemas in `contracts/schema/`), the policy rules they need and the errors you will meet. Then enrol a user and serve the state directory ([Run a real enclosure](docs/guides/RUNNING.md#run-a-real-enclosure-no-demo-data)).

**Sources, with Forge.** `forge-worker` re-reads its sources on a schedule and syncs them into the fabric while the gateway runs. Its connectors read CSV files, PostgreSQL queries, S3-compatible object prefixes and Kafka topics (`forge/connector-sdk/src/connectors/`). Under compose it runs the jobs in `deploy/compose/forge/jobs.json`, which is built into the image: add a job there and run `just compose-up` again. The jobs file format is documented in `forge/worker/src/lib.rs`, and `python3 samples/convert.py forge --out DIR` writes jobs and CSVs for the sample data.

**Feeds, into Heimdall.** A feed source signs each observation with its own certified mesh identity and submits it with `heimdall-source`, as the compose `feed-source` service above does. `python3 samples/convert.py observations` turns the recorded feeds into its input ([samples/README.md](samples/README.md#heimdall-observations)).

## Modifying and developing

Build, test and lint with `just`. Run `just` on its own to list every recipe.

```bash
just build        # cargo build --workspace --release, plus the JS, Go and Python members
just test         # the test suite, both crypto backends
just lint         # clippy at deny-warnings
just fmt          # cargo fmt; CI runs just fmt-check
```

Use `just test`, not `cargo test --workspace`: the crypto crates select their backend through mutually exclusive features, and a single workspace run would compile those tests out. Without a local toolchain, run any recipe in the pinned image, the way CI does:

```bash
bash tools/ci/in-toolchain.sh just test
```

Each CI job runs locally the same way as in the pipelines: `just ci list` names them, and `just ci <job>` runs one (for example `just ci claims` or `just ci numbers`). [docs/dev/CI.md](docs/dev/CI.md) explains them, and [docs/guides/VERIFYING.md](docs/guides/VERIFYING.md) covers the air-gapped acceptance gate and the supply-chain release gate.

Where the code lives:

| Path | What |
|---|---|
| `services/` | Midgard core: `http-gateway` (the edge), `iam`, `fabric`, `kms`, `governance`, `scheduler`, and `runtime` (the shared service runtime) |
| `crypto/` | `pqc-agility`, `pq-mtls`, `audit-writer`, `policy`, `attest` |
| `mimir/` · `forge/` · `bifrost/` · `heimdall/` | the four products, each with its running service (`mimir-server`, `worker`, `fleet-server`, `feed-server`) |
| `admin/` · `clients/` | admin libraries; the shared client core and the client shells |
| `tools/` | CLIs: `mg-admin`, `mg-model`, `mg-sign`, `mg-verify`, `mg-sbom`, `mg-scan`, `mg-repro`, `mg-bundle`, `mg-register` |
| `products/` · `ui/` · `sdk/` | console UIs (Vite and React), the design system, the generated SDKs |
| `contracts/` | proto contracts and the published JSON Schemas |
| `deploy/` | compose, kind, the Helm chart, images, the installer, the air-gap bundle, the acceptance gates |
| `docs/` | the specification (`dev/`), guides, operations, compliance and the design system |

**Adding a service or a connector.** A new service is a workspace crate with a `main.rs` built on `service-runtime` (`services/runtime`), which gives it a mesh identity, a durable audit ledger, the PQ-mTLS accept loop and health and metrics; the five existing services are the examples. A new Forge source implements the `Connector` trait in `forge/connector-sdk/src/connector.rs`, beside the connectors in `forge/connector-sdk/src/connectors/`. Add the crate to the workspace in `Cargo.toml` and to the `test` and `lint` recipes in the `justfile`. The release matrix is derived from the workspace, so a new binary is gated automatically; `supply-chain/release-artefacts.txt` records whether it ships as a service image or a tool.

**Pull requests.** Branch from `dev` and open the pull request into `dev`; `main` is updated from `dev` by pull request. A pull request needs one code-owner approval, and maintainers merge with a merge commit. Every commit must be signed with a key listed in `deploy/trust/allowed_signers`, and the `commits` job names any that is not. Changed sources cite the requirement they implement (the `provenance` job). [CONTRIBUTING.md](CONTRIBUTING.md) has the details, including how to sign with an SSH key.

## Releasing and installing offline

A release needs no forge. On a provisioned signing machine, with the tagged commit checked out, `bash tools/ci/run.sh release-offline <tag>` runs the whole release in order: it checks the signed tag, the machine and the gate record, then reproduces, describes (SBOM), scans, signs with ML-DSA and verifies every binary, builds the verify-before-run images, packs the signed air-gap bundle and publishes to a local directory with `SHA256SUMS`. On the disconnected site, `deploy/air-gap-bundle/install.sh` verifies that bundle offline and installs from it alone. See "Releasing without a forge" in [docs/ops/PKI.md](docs/ops/PKI.md#releasing-without-a-forge) and [deploy/air-gap-bundle/README.md](deploy/air-gap-bundle/README.md).
