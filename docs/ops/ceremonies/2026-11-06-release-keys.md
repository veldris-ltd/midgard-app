## Machine isolation

The ceremony machine's links, read at the moment the keys were generated. Dvalin reads
them afresh when GENERATE is confirmed, writes that reading into the record, and will
not open or continue the ceremony while any link is up, so the machine was offline
from before "Hold the ceremony" was chosen until Dvalin was closed:

- Wi-Fi off: radio off
- Ethernet disconnected: no wired adapter connected
- Bluetooth off: radio off, or no Bluetooth hardware
- NFC off: no NFC radio found
- Other links none: no virtual, VPN or mobile link up
- Read at 2026-11-06T20:59:22Z (UTC), from the operating system, sending nothing.

The first version of this record dated the generation 20:55:41Z and said the links were
read "just before the keys were generated", which did not agree. The earlier time is
when Dvalin was started: Dvalin 0.1.0 takes its clock once, at start-up, and writes that
as the generation time. The reading at 20:59:22Z is the generation itself, and the
keystores and the published files carry that time.

## Backup

Key fragmentation was not used. The backup is a copy of the keystores and the custody
register, made at 21:08Z and checked identical by digest.

Where it is. The keys folder is on an internal disk of the ceremony machine that is
BitLocker-encrypted (the Security Officer's statement, 7 November; the record's author
could not read the BitLocker status without administrator rights). That disk serves as
the `KEYS` drive of dvalin-app `docs/KEY_CEREMONY.md`, B3, though it is not removable.
On 6 November and until the morning of 7 November the only copy was a second folder on
that same disk; the first version of this record said "a second encrypted drive, held
apart from the first", which was the intended custody (B8), not what existed. On
7 November, before 10:49Z, a new external NVMe drive was formatted, encrypted with
BitLocker To Go and labelled `KEYS_BACKUP` (mounted as J:), and the backup folder was
copied to it. Two photographs of the drive and of the copy are kept outside the
repository, in the folder that held the backup on the ceremony machine. The duplicate
copy on the internal disk, with an accidental nested copy of the model-signing
keystore (`model\model\`) inside it, was removed on 7 November at 11:15Z; since then
the backup is the copy on `KEYS_BACKUP` alone.

On 8 November the copy on `KEYS_BACKUP` was checked by digest against the keys folder
(`Get-FileHash`, SHA-256, in an administrator PowerShell): the four keystores match in
both places, release `a67b4e09…`, Bifrost `37638330…`, model-signing of 01:42Z
`982c614e…`, and the unpublished first key `3a306e85…`, which is therefore on
`KEYS_BACKUP` as well and must be destroyed there too.

## The model-signing key, generated 7 November

`deploy/trust/model-signing.pub` was not written by Dvalin: Dvalin 0.1.0 generates only
the release and admission keys, and the separate `mg-model keygen` step
(`docs/ops/KEY_CEREMONY.md`, "The model-signing key") was not run on 6 November, because
`mg-model` had not been built on the ceremony machine. The omission was found in review
(7 November, 00:13Z). The key was generated in a follow-up session on 7 November, on the
ceremony machine, with the Security Officer and the witness present throughout and the
machine offline; both people checked the links by hand, since Dvalin was not running
and there is no reading from it.

What was done, and where it differed from the procedure the first version of this
section set out:

1. `mg-model` was built in the ceremony checkout, by then at `4e21e26` on this branch,
   whose source differs from `ebd0aeb` only in `deploy/trust/` and this record:
   `cargo build --release --locked --bin mg-model` (01:28Z).
2. The keystore passphrase was generated in the password manager as the entry
   "Midgard model-signing keystore 2026", 16 characters, the witness present, and typed
   back from the password manager to confirm. It was written to a file outside every
   checkout and off the keys folder from a masked PowerShell prompt
   (`Read-Host -AsSecureString`), not Notepad, and handed to `mg-model` with
   `--keystore-passphrase-file`, not the environment variable. Two earlier attempts to
   write that file failed: the first wrote an empty file, which `mg-model` refused
   ("the passphrase file is empty"); the second showed a candidate passphrase on the
   screen. That candidate was discarded and never used; the passphrase in use was
   generated afresh afterwards and is not the one shown.
3. Generated at 01:42:11Z with key id `midgard-model-2026`, into
   `midgard-keys_2026\model\`, a subfolder beside the two keystores, as
   `model-signing.keystore` (format 3) and `model-signing.pub`. `mg-model keygen` runs
   no self-test; the key is first exercised when a model manifest is signed with it
   and verified against the published file.
4. The `model` folder was copied to the backup folder at 01:44Z; the copies match by
   SHA-256 (see "Backup" for where that folder is).
5. `model-signing.pub` was copied to `deploy/trust/model-signing.pub`, SHA-256
   `58941dee250ebfac9dc9463ae8d4949152cb600469108e3c58329b2c00bc398f`, and committed
   signed as `c37f6cd` at 01:45:10Z, with no change to this record. This update is
   that change. The commit's title, "model-signing key, 6 November 2026", names the
   ceremony the key belongs to; the commit was made on 7 November, as the timeline
   says. The title is left as it is, because changing it would rewrite a pushed,
   signed commit.
6. Close-out, before this update was committed: the passphrase file was deleted, and
   the machine's disks were searched for `*.passphrase` and for `*.keystore` outside
   the keys folder and its backup; none remained. The machine went back online only
   after that.

   **Correction, 9 November.** The statement above, made in `bf86295`, was wrong on
   one point: the passphrase file (`C:\Users\t3kao\model.passphrase`, 16 bytes, written
   7 November 01:41:50Z) had not been deleted. It was found still on the ceremony
   machine's disk on 9 November and deleted at 01:30:00Z. It held the passphrase of the
   published model-signing keystore, which is also recorded in the password manager;

### A first key that was not published

Before the session above, at 00:46:30Z, `mg-model keygen` had been run once with an
`mg-model` built at 00:35Z in the development checkout on the same machine (branch
`security-patch_oct`, not the ceremony checkout). It wrote `model-signing.keystore` and
`model-signing.pub` into the root of the keys folder, with the same key id
`midgard-model-2026`. That keystore is format 1, whose root is not wrapped under a
passphrase, so the file alone is the private key; the ceremony checkout's `attest`
refuses to read it. Its public half (SHA-256
`d706bf461446202570d325c9b39561b7ea99946045982b18ebd09355bc55f6a6`) was never committed
or published, and nothing has been signed with it. There were three copies of the two
files: in the root of the keys folder, in the backup folder on the internal disk, and
on `KEYS_BACKUP` (confirmed by the digest check of 8 November). The copy in the backup
folder on the internal disk went with that folder on 7 November at 11:15Z. On
9 November at about 00:00Z the Security Officer destroyed a copy (their statement;
which copy is not stated). As of 9 November 01:01Z the two files were still in the
root of the keys folder on the ceremony machine. Between 01:01Z and 01:18Z the
Security Officer removed them from the root of the keys folder and from `KEYS_BACKUP`
in one administrator PowerShell command, then listed every `model-signing.keystore`
and `model-signing.pub` under both places recursively with their SHA-256: only the
published key's two digests appear, `982c614e…` for the keystore and `58941dee…` for
the public file, once in the keys folder and twice on `KEYS_BACKUP` (the copy and its
accidental nested duplicate). No copy of the first key remains in either place. The
witness's presence at the destruction is not recorded here; the witness confirms it,
or not, in the sign-off. The key is destroyed material, never a trust anchor: nothing
verifies against it, and a file with its public digest, if one were ever found, would
be a copy that escaped, to be reported.
