# Midgard v0.1.0-rc.2 — release candidate

> **This is a release candidate, not a supported release.** It exists to run the whole
> release pipeline end to end. Do not run it in production. GA is **NO-GO**: the
> blockers are listed under "What this candidate is not", and recorded in
> `docs/compliance/GA_READINESS.md`.
## Why a second candidate

`v0.1.0-rc.1` was tagged on 2026-11-09, at `3568b9b`, and its release run never reached
the signing jobs. Three faults in the release workflow stopped it, one after another:

- the checkout made for a tag's own run replaces an annotated tag with a lightweight
  one, so the tag check refused it (#91);
- the workflow passed neither keystore's passphrase file to the signing runner (#92);
- the release job needed every shell-audit job to succeed, and GitHub cancels the apple
  audit before it starts, because its macOS 14 image is retired (#92).

A release tag cannot be moved, and a tag's run uses the workflow files of its own
commit, so no re-run of rc.1 can release it. `v0.1.0-rc.2` is the same platform with
those three fixes; apart from the version and the records that go with it, nothing
else changed. `v0.1.0-rc.1` stays tagged, and was never released.


## What this candidate is

The first build of Midgard as a platform that can be deployed and used, rather than a
set of verified libraries:

- **The edge on the real enclosure.** The HTTP edge serves the object fabric and its
  single governance spine, with one PQ-signed audit ledger.
- **Persistent state.** Keys, policy, ontology and users are durable, with offline and
  dual-control online enrolment through `mg-admin`.
- **Five services.** `http-gateway`, `mimir-server`, `bifrost-fleet`, `heimdall-feed`
  and `forge-worker` run on one PQ-mTLS service runtime. They deploy with Docker
  compose, or with a Helm chart that runs on Kubernetes.
- **Forge connectors.** PostgreSQL, S3 and Kafka, with an egress broker (TLS 1.3, a
  pinned CA per route) for sources outside the enclosure.
- **Model serving.** A real model behind `mimir-server`: llama.cpp on CPU, vLLM on GPU.
  A model loads only from a signed manifest whose weights stream to the signed digest.
- **A release pipeline.** Every binary is gated. The services become verify-before-run
  images, and a signed air-gap bundle carries the verified set. An installer verifies
  that bundle offline and deploys it.

The full list is in `CHANGELOG.md`.

## What this candidate is not

It is not generally available, and nothing about the tag says otherwise.
`docs/compliance/GA_READINESS.md` records **NO-GO**, and each of these blocks GA:

- **Open residual risks.** The risk register's 15 PARTIAL rows, nine of them High
  severity, are carried by open `RF-*` items (`docs/compliance/RESIDUAL_RISK_REGISTER.md`).
- **The acceptance suites and shell audits on release infrastructure** (GA_READINESS §4
  A–B). The gate record for this tag is a run in the pinned toolchain image, not on the
  release infrastructure, and the client shell audits fail closed until every shell has
  a buildable project. No shell exists yet, so this candidate's audits are waived, as a
  recorded owner decision for `0.1.0-rc.2` only (`clients/shells/audit-waivers.txt`);
  a final release cannot be waived.
- **The per-artefact gate on the signing runner, with ceremony keys** (§4 C). It has
  been rehearsed only with throwaway drill keys.
- **FIPS 140-3 module certification** (§4 D), which is external: the in-repo KATs pass,
  the CMVP certificate does not exist.
- **Deployment-tier assurance** (§4 E): real HSM custody, GPU inference and a
  multi-node cluster. The rehearsal on kind exited 3, a partial pass.

The figures this candidate states are those of
[`docs/compliance/NUMBERS.md`](../compliance/NUMBERS.md) and the gate record it names,
both at the tagged commit; each capability's status is in
[`docs/compliance/CLAIMS.md`](../compliance/CLAIMS.md).

## What has been proven, and how

**Services on one machine.** `just compose-smoke` passes:

- inference over PQ-mTLS, audited, which continues its ledger after a restart;
- a fleet check-in and convergence;
- fused feed observations;
- a Forge sync into the fabric.

**Services on Kubernetes.** On a three-node kind cluster (Kubernetes 1.33),
`just kind-smoke` passes with Granite serving. It covers the same flows, and a pod
outside `mimir-server`'s policy cannot reach it.

**Deployment tier (RC-40), on kind, 2026-09-15.** Exit 3: a partial pass, not a
promotion. The model and engine here are Granite 3.3 2B on llama.cpp.

| Check | Result |
|---|---|
| RC-40.1 | **PASS**: every service rolls out, restarts, re-verifies its ledger and comes back ready |
| RC-40.2 | **PASS**: a hybrid X25519 + ML-KEM-768 handshake between pods on two nodes |
| RC-40.3 | **SKIP**: no HSM |
| RC-40.4 | **SKIP**: no GPU. Before skipping, it made a live certified PQ-mTLS call answered by that model on CPU: 32 tokens, first token in 572 ms |

**Model serving.** `just compose-granite-smoke` passes: 44 tokens, first token in
325 ms, on a 12-core arm64 host. A changed weight byte stops the service from starting.

**Connectors.** PostgreSQL 16 and MinIO pass live tests, as does S3 through the egress
broker to a TLS server. The Kafka connector has been tested only against a fake broker.

**Release pipeline.**

- `supply-chain/release-artefacts.txt` covers all 18 binaries the workspace builds, and
  a new one fails the check.
- The signing-runner preflight fails closed, naming each missing key, secret and anchor.
- **The pipeline has been rehearsed end to end on 2026-09-15.** The rehearsal used
  throwaway drill keys, which were never committed or published (see
  `docs/compliance/GA_READINESS.md` §4a):
  - all 18 binaries were gated, and every attestation records its source revision;
  - 6 images were built, each binary verified and started through its image's own
    entrypoint;
  - a 54-artefact bundle was packed, then installed on kind with `install.sh`;
  - the kind smoke test passed on the release images;
  - the deployment tier exited 3 (RC-40.1 and RC-40.2 passed);
  - an image with one changed byte refused to start.

## Artefacts

A tagged run of the release workflow produces:

- **Every binary** in `supply-chain/release-artefacts.txt`, each with its `.sig`,
  `.att` and `.sbom.cdx.json`. Check one with
  `mg-verify <binary> --trust-anchor deploy/trust/release-trust.pub`.
- **`images.lock`**, the verify-before-run images built from those binaries, signed
  like a binary.
- **`midgard-0.1.0-rc.2.mgbundle`**, the air-gap bundle. Install it offline with
  `bash deploy/air-gap-bundle/install.sh BUNDLE --bundle-trust deploy/trust/bifrost-trust.pub --push`.

## Known limits

- **Key custody is software.** Keystores are files, sealed under a key held in the same
  file. No HSM is wired in.
- **GPU serving is unproven.** Model serving on GPU (vLLM) has not run, so the 800 ms
  first-token target is unproven.
- **Connector gaps.** PostgreSQL cannot use the egress broker before PostgreSQL 17, and
  the Kafka connector has not met a real broker.
- **Mock consoles.** Consoles other than Midgard's run on mock data.
- **One replica per service.** Each service holds a single-writer state directory.
  Availability comes from restart and recovery, not replicas.

## How this candidate is cut

The key ceremony, the signing runner, the artifact storage and the repository rules
are in place, from rc.1. A decision on disclosing the design documents is still the
owner's to take before any non-draft release.

1. **The waiver.** The owner records the decision for `0.1.0-rc.2` in
   `clients/shells/audit-waivers.txt`; without that line the shell-audit gate refuses
   this candidate.
2. **The gate record.** Run the gate on the commit to be tagged, the tip of `main`,
   and record it, then write the numbers sheet (`docs/dev/CI.md`, "The gate record");
   merge that records-only change.
3. **The tag.** `bash tools/ci/tag-release.sh` makes the signed tag once the gate
   record, the numbers sheet and the claims ledger all cover it. Push the tag: the
   release workflow verifies it, runs the signing-runner preflight and the shell-audit
   gate, then gates, admits and accounts for every artefact. A second maintainer
   approves each job on the signing runner.
4. **The draft.** Run the workflow manually on the tag with `publish` set to
   `v0.1.0-rc.2`, for a draft pre-release with the gate logs and the numbers sheet
   attached.
